# iPerf2 / iPerf3: исследование генерации трафика

Воспроизводимое исследование того, насколько точно **iPerf2 и iPerf3 создают заданную сетевую нагрузку**: выдерживают ли нужную скорость, воспроизводят ли периоды передачи и паузы, как меняется результат при ограничении процессорного времени. Репозиторий содержит Python-автоматизацию, сценарии экспериментов, реальные измерения, захваты пакетов и графики.

## Зачем проводилось исследование

В сетевом эксперименте обычно предполагается, что генератор создаёт именно тот поток, который ему задан. Но команда «отправлять 200 Мбит/с» ещё не гарантирует такую скорость: отправитель может упереться в CPU, а приёмник — потерять часть пакетов в очереди сокета. Совпадение средней скорости также не гарантирует правильного чередования активных интервалов и пауз.

**Цель работы - проверить сам источник нагрузки, прежде чем делать выводы о сети.** Для этого отдельно сопоставляются заданный профиль, фактическая скорость отправки (TX), скорость приёма (RX), времена пакетов и потребление CPU. Такой подход помогает отличить недостаток производительности генератора от потерь на принимающей стороне и неточности измерения времени.

## Какие задачи решает эта работа

| Направление                        | Исследовательский вопрос                                                                                                    | Что сделано                                                                                                                                                                                                                                                                                                           |
| --------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Сравнение UDP-генераторов | Достигают ли iPerf2 и iPerf3 одинаковой целевой скорости при одинаковых условиях?        | Автоматизированы повторы с разными скоростями, размерами пакетов и CPU-квотами; измеряются TX/RX, PPS, CPU и потери                                                                                                                           |
| ON/OFF на iPerf2                            | Можно ли получить поток «передача → пауза → передача» с нужными длительностями? | Проверены `--isochronous`, `--ipg` и burst-опции; реализованы периодические и случайные интервалы с проверкой по захвату пакетов                                                                                                        |
| FTP-like TCP на iPerf3                      | Как воспроизвести конечные передачи данных с паузами чтения между ними?               | Реализованы последовательные передачи через `-n`, разные размеры файлов и экспоненциальные паузы по параметрам FTP Model 2; отдельно измеряются сетевой интервал и время процесса |
| Контроль буфера                 | Если RX ниже TX, связано ли это с буферизацией?                                                                   | Часть UDP-опытов повторена с увеличенным буфером сокета                                                                                                                                                                                                                            |

Прямое сравнение iPerf2 и iPerf3 выполняется **при одинаковой UDP-нагрузке**. ON/OFF и FTP-like исследуют разные профили трафика; они не используются как сравнение UDP с TCP в одной задаче.

## Как проводились эксперименты

Измерения выполнены на Ubuntu 24.04 с iPerf2 2.1.9 и iPerf3 3.16. Сначала проверялись версии и опции инструментов, затем короткие локальные тесты, после них — основная серия с повторениями и отдельный контроль буфера.

Отправитель и приёмник работали на одной машине через loopback, на разных физических ядрах. Квоты cgroup v2 ограничивали **только отправителя**: без квоты, 100%, 50% и 25% одного логического CPU. Во всех режимах отправитель оставался закреплён за одним CPU. Для ON/OFF и TCP сохранялись PCAP, чтобы проверять временную структуру независимо от отчётов iPerf.

В репозитории сохранены результаты **105 UDP-тестов, пяти ON/OFF/burst-сценариев и 12 TCP-передач**, а также 14 графиков PNG/SVG. Исходные команды и вывод инструментов позволяют проверить, откуда получено каждое число.

## Что показала пилотная серия

- **CPU может ограничить саму создаваемую нагрузку.** При цели 200 Мбит/с, UDP payload 128 байт и квоте 25% средний TX составил 125,74 Мбит/с у iPerf2 и 118,47 Мбит/с у iPerf3. Поэтому заданную скорость нельзя автоматически считать фактически отправленной.
- **Потери приёма нужно отделять от недогенерации.** В контроле iPerf3 при 200 Мбит/с, payload 1200 байт и квоте 25% увеличение запрошенного буфера с 1 до 4 МиБ снизило средние потери с 17,55% до 0% при близком TX. Это указывает на влияние буферизации в данных условиях.
- **ON/OFF требует проверки по пакетам.** `--isochronous` вместе с `--ipg` дал профиль, близкий к выбранным ON=100 мс и OFF=200 мс. Отдельный процесс на каждый ON добавляет задержки к паузе; burst-опции в проверенном UDP-режиме нужного профиля не дали.
- **Время короткой TCP-передачи зависит от способа измерения.** Для 500000 байт в сценарии Model 2 сетевой интервал до полного ACK составил 0,095–0,202 мс, тогда как iPerf3 сообщил около 100 мс. Время жизни процесса, отчёт iPerf3 и время передачи данных нужно рассматривать отдельно.

Это результаты коротких localhost-опытов для указанных версий и хоста. Точный ON/OFF и точная последовательность фактических пауз FTP Model 2 не обеспечиваются: отклонения измерены и описаны. Удалённый режим предусмотрен в конфигурации, но реальными испытаниями не проверялся.

## Быстрый запуск на Ubuntu 24.04

Из корня этого каталога, под обычным пользователем с рабочим `systemd --user`:

```bash
sudo apt-get update
sudo apt-get install -y iperf iperf3 tcpdump python3 python3-matplotlib
python3 -m netperf_lab doctor --output results/my-environment
python3 -m unittest discover -s tests -v
```

Локальные бинарники в `.tools/root` имеют приоритет над системными. Альтернатива системной установке iPerf — распаковка зафиксированных Ubuntu-пакетов без root:

```bash
sh scripts/bootstrap-local.sh
```

Если старые версии исчезли из зеркала, используйте архив Ubuntu либо системные пакеты и заново проверьте справку и PCAP; переносить выводы между версиями автоматически нельзя. Сетевые библиотеки не подменяются глобально: `LD_LIBRARY_PATH` задаётся только дочерним процессам. В `.tools/` сохранены скачанные `.deb`; их SHA256 также записаны в окружении каждого запуска.

Для обычной Ubuntu настройте захват через `sudo`, предварительно получив разрешение в своём терминале:

```bash
sudo -v
python3 - <<'PY'
import getpass, json
from pathlib import Path
for name in ['smoke', 'research-local']:
    config = json.loads(Path(f'configs/{name}.json').read_text())
    config['capture_command'] = ['sudo', '-n', 'tcpdump', '-Z', getpass.getuser()]
    Path(f'/tmp/iperf-{name}.json').write_text(json.dumps(config, indent=2))
PY
python3 -m netperf_lab run /tmp/iperf-smoke.json --output results/my-smoke
python3 -m netperf_lab analyze results/my-smoke
sudo -v
python3 -m netperf_lab run /tmp/iperf-research-local.json --output results/my-research
python3 -m netperf_lab analyze results/my-research
```

Ожидаемая длительность основной серии — несколько минут. Каждый запуск требует **новый или пустой** выходной каталог; старые измерения не перезаписываются. Логи можно перенаправить в отдельный файл. Установка matplotlib через pip при необходимости: `python3 -m pip install -r requirements.txt` внутри venv; генераторы используют стандартную библиотеку Python.

## Воспроизведение поставленных измерений на этом хосте

В сохранённых конфигурациях используется отдельный Docker-контейнер для tcpdump, поскольку прямой захват недоступен пользователю. Образ уже был локально доступен; существующие контейнеры не изменяются. Нужны доступ к Docker и образ, указанный в `scripts/docker-tcpdump.sh` или `CAPTURE_IMAGE`. Контейнер имеет только `NET_RAW`, файловая система и подключённые tcpdump/библиотеки доступны только для чтения. Это Linux/x86-64 вариант; обычный `sudo tcpdump` выше переносимее.

```bash
sh scripts/bootstrap-local.sh
python3 -m netperf_lab run configs/smoke.json --output results/repeated-smoke
python3 -m netperf_lab run configs/research-local.json --output results/repeated-research
python3 -m netperf_lab analyze results/repeated-research
python3 -m netperf_lab run configs/socket-buffer-control.json --output results/repeated-buffer-control
python3 -m netperf_lab analyze results/repeated-buffer-control
python3 scripts/audit_results.py results/repeated-research
python3 scripts/audit_results.py results/repeated-buffer-control
```

В Codex эти сетевые команды и `systemd-run --user` требуют запуска вне песочницы. Прямая проверка cgroup/сокетов из песочницы не характеризует возможности обычного пользовательского терминала.

## Сценарии и параметры

JSON содержит один сценарий либо массив `scenarios`; общие параметры наследуются. `seed=814` фиксирует порядок опытов и случайные интервалы. Порядок UDP-тестов перемешан, опыт выполняется последовательно. Параллельные тесты исказили бы CPU-ограничения.

| Сценарий                  | Основные параметры                                                                                                                                                         |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `udp_matrix`                    | `tools`, `rates_bps`, `packet_sizes`, `duration_s`, `repeats`, `cpu_quotas_percent`                                                                                             |
| `onoff`, `method=isochronous` | фиксированные `on_s`, `off_s`, `cycles`, `on_rate_bps`, `packet_size`, необязательный `ipg_unit`                                                     |
| `onoff`, `method=sessions`    | те же параметры; интервалы могут быть фиксированными, равномерными или экспоненциальными                       |
| `onoff`, `method=burst_probe` | исследовательская проверка `--burst-period`/`--burst-size`; результат **не считается** ON/OFF без подтверждения PCAP |
| `ftp`                           | `transfers`, `file_sizes_bytes`, `reading_time`, `report_interval_s`, `capture_tcp`                                                                                               |

Примеры интервалов: `0.2`, `{"distribution":"uniform","min_s":0.1,"max_s":0.3}`, `{"distribution":"exponential","mean_s":5}`. Отрицательные интервалы запрещены. IPv4 UDP payload ограничен 64–1400 байт; для удалённого пути с меньшим MTU размер нужно уменьшить дополнительно. Все скорости — десятичные бит/с, размеры файлов — целые байты; 0,5 MB здесь означает **500000 байт**.

Квоты `null`, `100`, `50`, `25` соответствуют отсутствию квоты либо доле **одного логического CPU**, а не доле всего компьютера. Отправитель всегда закреплён за одним CPU, включая `null`; приёмник закреплён за другим физическим ядром, без собственной квоты. Выбор сохраняется в `placement.json`, при необходимости задайте `sender_cpu`/`receiver_cpu`. CPU-квота проверяется по реальному `cpu.max`; период — 100 мс. Cgroup содержит sender-worker и его iPerf, приёмник и монитор остаются снаружи. Проверяются и сохраняются квоты предков. Нет автоматической подмены квоты на `SIGSTOP`/`SIGCONT`.

Если пользовательский CPU-controller недоступен, запуск с квотой завершится ошибкой. Для **только неограниченных** тестов можно явно выбрать `cpu_backend="none"` и квоты `[null]`. Это не воспроизводит CPU-серию.

## Семантика ON/OFF

Для native-аппроксимации вычисляются:

```text
period = on_s + off_s
fps = 1 / period
mean_bps = on_rate_bps * on_s / period
ipg_seconds = packet_size * 8 / on_rate_bps
```

Параметр `--isochronous=fps:mean_bps,0` задаёт периодические кадры с нулевой вариацией объёма. `--ipg` растягивает пакеты внутри кадра. `-b` одновременно с этими флагами не передаётся: iPerf2 2.1.9 отвергает такую комбинацию. В этой версии `--ipg` фактически использует **миллисекунды**; локальная man-страница и актуальное web-руководство расходятся со справкой и измерением. Сохранён отдельный двухвариантный PCAP-тест в `results/ipg-probe`. Для другой версии единицы необходимо подтвердить захватом; неизвестная единица вызывает ошибку, либо задаётся явным `ipg_unit` после калибровки.

Это пакетная аппроксимация: возможны служебные пакеты, квантование объёма, пропуски расписания и неполный последний кадр. Под CPU-квотой ON/OFF может нарушаться. Генератор не обещает точный аппаратный timing.

`sessions` запускает отдельный iPerf2 на каждый ON и планирует OFF после завершения процесса. Пауза на линии дополнительно включает завершение обмена и запуск следующего процесса; это **не точный периодический gate**. Случайные ON/OFF реализованы этим способом. Native isochronous не выдаётся за генератор произвольных случайных пауз.

PCAP сохраняется с `--immediate-mode -U -s 160`. Анализ использует положительный iPerf2 sequence ID и заданную длину UDP payload; отрицательные FIN и обратные отчёты исключаются. Это timing data-пакетов заданного размера, а не гарантия полного молчания интерфейса в OFF. Порог группировки `gap_threshold_s` задаётся явно; под квотой разрыв внутри ON может быть ошибочно разделён на несколько пачек. Для проверки служат `packets.csv`, `bursts.csv` и график, а не только число пачек. Захват с ненулевыми или неизвестными kernel drops считается ошибкой. Loopback имеет удвоенный счётчик `received by filter` в Linux; он не равен числу записей PCAP.

## FTP-like и FTP Model 2

Используется `iperf3 -n N` с новым TCP-соединением на каждый файл, один пользователь (`K=1`). Реальный FTP-протокол и чтение файла с диска не моделируются. Для Model 2 выбраны S=500000 байт и независимое D~Exp(mean=5 с), по TR 36.814, A.2.1.3.1. Один пользователь не является полной многопользовательской системной симуляцией 3GPP. `ftp-sizes` и короткий smoke с другими паузами — отдельные прикладные сценарии.

TCP `-l` выбирается делителем N, не больше 65536 байт, чтобы избежать передачи лишнего блока при `-n`. Для 500000 байт это 62500 байт. Неудобные размеры, например простое N, могут потребовать очень маленького блока и изменить CPU-нагрузку; поле `block_bytes` сохраняется. Можно задать собственный делитель через `block_bytes`.

Сохраняются три разные длительности:

1. `transfer_seconds`/`tx_bps`: итоговые данные iPerf3, включающие его механизм завершения теста.
2. `process_wall_s`, `sender_cpu_s`: полная жизнь процесса и CPU всех его потоков через `wait4`, включая управление.
3. `pcap_completion_ack_span_s`: от первого байта файла на отправителе до первого cumulative ACK, покрывающего весь файл. Это сетевой интервал без установки соединения и финального обмена iPerf3; он не измеряет запись файла приложением на диске.

TCP-анализ выделяет соединение с наибольшим объёмом payload, исключает 37-байтный cookie iPerf3, объединяет диапазоны sequence number, учитывая retransmits и wraparound, и проверяет весь размер файла. Он рассчитан на используемый iPerf3 3.16 и IPv4 classic-PCAP; TLS/PCAPNG/IPv6 не поддерживаются. Для очень маленьких файлов, сравнимых с управляющими сообщениями iPerf3, выбор потока неприменим. В поставленных сценариях N≥500000.

При TCP-PCAP чтение D отсчитывается от полного ACK предыдущего файла; без PCAP — от завершения процесса iPerf3. Следующий запрос может опоздать из-за управления, запуска cgroup и установки соединения. Фактический интервал ACK→следующий SYN сохраняется в `pcap_actual_reading_s`, а выборка D — отдельно; малое D не выдаётся за точно воспроизведённое. OFF после последнего файла не добавляется. Часы PCAP — wall clock, планировщика — monotonic; предполагается отсутствие скачка системных часов во время короткого опыта.

## Данные и проверка узкого места

Каждый опыт сохраняет команды, stdout/stderr, конфигурацию, версии/справку, SHA256 бинарников и исходников, CPU affinity, `cpu.max`, `cpu.stat` до/после, CPU-сэмплы с периодом 50 мс, `/proc/net/snmp`, softnet counters и состояние host CPU. Сэмплы коротких процессов могут отсутствовать; точный sender CPU всё равно берётся из `wait4`. Receiver CPU — оценка по `/proc`, для очень коротких TCP-передач она не является точной оценкой CPU сетевого интервала.

`source-hashes.json` фиксирует код в начале генерации; `postprocessing-source-hashes.json` — отдельную версию анализа и аудита при построении графиков. Исправления оформления графиков после измерений не изменяют raw-данные. `scripts/audit_results.py` проверяет неизменность кода генерации, квоты, повторения, размеры и PCAP; сохраняет `verification.json` и host-wide UDP counters в `host-udp-diagnostics.csv`.

UDP iPerf2: sender bps берётся из его CSV, receiver — из отдельного server CSV; округлённые до 0,1 с endpoints не используются для пересчёта точного sender bps. PPS выводится из payload bps и фиксированного размера. UDP iPerf3: `sum_sent` и `sum_received` из JSON. Потери относятся к приёмнику; недогенерация отправителя считается отдельно как `100*(tx_bps/target_bps-1)`. Внутренние CPU-оценки iPerf3 сохранены отдельно от независимого учёта.

У обоих инструментов один поток данных, одинаковые payload, target, длительность, буфер сокета 1048576 байт и размещение CPU. Pacing-алгоритмы инструментов различаются; у iPerf3 явно задан штатный `--pacing-timer 1000`. Capture не запускается во время UDP CPU-матрицы. Различия pacing и служебного обмена не устраняются и относятся к предмету сравнения.

TX ниже цели вместе с исчерпанной квотой и throttling указывает на ограничение отправителя. RX ниже TX, потери и высокая загрузка приёмника требуют отдельной проверки приёмника/сети. Loopback исключает физическую сеть, но kernel/softirq могут исполняться и вне cgroup отправителя. Receiver affinity не изолирует весь kernel datapath. Фоновая нагрузка и энергосбережение не отключались. Не следует объявлять причиной любой потери только CPU отправителя.

Агрегация: среднее, выборочное SD, min/max, n; на графиках среднее ± SD, не доверительный интервал. Три повтора по 2 с — пилотное сравнение, а не установившаяся оценка производительности оборудования. Для публикации увеличьте `duration_s` и `repeats`, используйте выделенные хосты и контроль загрузки приёмника.

## Удалённый приёмник

Шаблон `configs/remote-ssh.example.json` использует SSH с ключами (`BatchMode=yes`), без автоматической установки ПО на другой машине. Замените оба адреса, SSH-имя и пути к бинарникам; откройте диапазон `base_port .. base_port+число_опытов-1` TCP и UDP. iPerf3 использует TCP control даже для UDP. Проверяются удалённые `--help`, server stdout сохраняется локально. iPerf2 server ограничен по времени, чтобы не оставлять бесконечный процесс при обрыве SSH. Удалённый receiver CPU через `/proc` не измеряется; его проверяйте отдельным монитором на приёмнике.

```bash
cp configs/remote-ssh.example.json configs/my-remote.json
# Edit receiver.host, receiver.ssh_host, binaries and desired scenarios.
python3 -m netperf_lab run configs/my-remote.json --output results/my-remote
python3 -m netperf_lab analyze results/my-remote
```

Также есть `receiver.mode="external"`: вы сами запускаете постоянные серверы и задаёте `receiver.port` для фиксированного порта. Для iPerf2 отсутствует локальный server CSV, поэтому RX/loss сохраняются как `null`, а не ноль. iPerf3 возвращает server summary по control connection. Для remote ON/OFF/FTP-PCAP задайте реальный интерфейс отправителя вместо `lo`; синхронизация часов с приёмником не требуется для sender-side timing. **Удалённый режим в этой поставке не проверялся реальными опытами.**

## Структура

- `netperf_lab/`: генераторы, runner, cgroup worker, CPU-учёт, PCAP-анализ и matplotlib.
- `configs/`: smoke, полная локальная серия, burst-проба, SSH-шаблон.
- `results/research-2026-10-28/`: основная измеренная серия; `results.csv`, `summary.csv`, PNG/SVG, raw trial-каталоги.
- `results/smoke-*/`, `results/ipg-probe/`, `results/tcp-duration-probe/`: промежуточные проверки, включая неуспешные; статус и причины не скрываются.
- `references/`: локальные справки, проверки парсера и ссылки на первоисточники.
- `tests/`: проверки разбора CSV/PCAP, точного размера файлов и случайных интервалов.
